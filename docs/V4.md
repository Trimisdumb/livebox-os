# V4 development guide

V4 is developed on `develop/v4`. It is not a 4.0.0 release. The package and API retain the 3.0 baseline until the remaining work is complete. The original desktop and operational V3 tools remain available through **Bureau classique**. This branch does not upgrade an existing installation automatically.

## Install and migrate

Use the [Windows/Linux installation guide](INSTALL.md) and select the development branch before building:

```sh
git clone --branch develop/v4 https://github.com/Trimisdumb/livebox-os.git
cd livebox-os
docker compose up -d --build --wait
```

Use a separate clone, Compose project name and volume when evaluating V4 alongside another installation. Never point a development container at the production data volume. Existing databases receive additional `control_*` tables; existing account, profile, incident and NAT tables are retained. Back up the application before an intentional migration. V3 application backups do not yet include the new registry and monitoring tables; stop the test instance and back up its data volume separately if you need those records.

No router password belongs in `.env`. Set up the local administrator through the existing host-pairing process, then enter router credentials in the authenticated application. New connector passwords are used for login and discarded; session credentials stay in backend memory. Connections need to be re-established after expiry, logout or restart.

## Navigation

The network view groups the requested categories into network inventory, access/protection, operations and application settings. Search finds destination names. It is not a full-text search of every individual router parameter. Phone, USB/SMB, profiles, wallpapers, application backups and the original double-NAT tooling remain reachable.

The dashboard has simplified, advanced and administrator presentation modes. These are layouts, not access roles. The application still has one local administrator account. Do not give untrusted users that account as a substitute for a read-only role.

Widgets and density are saved per browser. Light/dark mode and desktop wallpapers use existing preferences. Non-sensitive export/import includes widget selection and density only. The UI is currently French; a complete English interface and accent customization remain pending.

## Add a router

1. Open **Routeurs**, then **Ajouter un routeur**.
2. Enter a name and address. Choose the connector whose model and protocol match your device.
3. Choose a collection interval of 30 to 3,600 seconds and acknowledge authorization to administer that device.
4. Save the profile, then **Tester et connecter** with the router credentials.
5. Open individual reads to inspect the actual responses and supported functions.

**Lire les passerelles du backend** reads the operating system's routing table. It performs no subnet sweep, discovery login or port scan. A Docker gateway can be returned; it is not proof that a compatible router has been found. Hostnames are resolved to authorized IPv4 addresses and pinned for the connection. HTTPS still verifies certificates; pinning to an IP requires a certificate valid for that IP. No certificate bypass is offered.

Names and collection intervals can be edited. Changing the connection address or protocol currently requires a new profile. Removing a profile closes its sessions but does not remove network rules; historical samples and notification records are retained until normal retention applies.

The new registry's TP-Link/Livebox sessions are separate from the original V3 sessions used by NAT and Wi-Fi editors. For those editors, connect the equipment in **Livebox** and in **Routeurs > Connexion TP-Link existante et NAT compatible**. A registry connection is not automatically promoted into a V3 write session.

## Livebox features

The original Wi-Fi enable/disable, SSID/password, radio-channel, DHCP and NAT editors keep their existing preparation/confirmation workflows. Additional read-only views cover the guest network, schedules, IPv4/IPv6 firewall level, WAN ping response, DMZ, DynDNS and firmware reboot history when the API returns data.

Registry Liveboxes can prepare guest-Wi-Fi changes, IPv4 firewall-level changes and reboot requests. A successful prior read is required. The user must type the device's current name, within two minutes, to confirm a single-use token tied to their session. Guest/firewall state is read again; concurrent changes block the write. After a timeout, the result is unknown rather than silently retried. A reboot acknowledgement is not proof that the reboot finished.

These additional reads/writes were implemented from the referenced protocol and tested with isolated fixtures. They have not been exercised against the owner's real network during V4 development. Factory reset and router configuration restoration are intentionally unavailable.

## Monitoring and notifications

Connected registry resources collect at their chosen interval. The backend retains at most 20,000 metric samples across resources and seven days of history. Sample exports contain observed reachability, uptime, connection state and optional ping latency/loss, not device lists, SSH output or credentials. No sample is created before a real backend read attempt; a gap after logout is not counted as downtime.

The optional ping checkbox authorizes four ICMP requests per collection interval. It is off by default. English/French Windows and Linux output formats are parsed for average latency and packet loss; unfamiliar formats, missing tools or timeouts stay unavailable rather than becoming zero. History shows measured latency bars, timestamps and loss values. A ping response and an authenticated API response are distinct observations.

Create notification rules for a connected resource becoming unreadable, a new device identity appearing, or a WAN address changing. Evaluation uses successive observations, so there is no alert for a first baseline. Rules persist, but collection requires an active authenticated session. No notification data is sent to an external service. **Tester la notification** creates an explicitly labeled manual test in the notification history; it does not change the network. Notifications can be acknowledged.

Bandwidth threshold rules, periodic reports, notification-category preferences and unattended collection across restarts are pending. V3's live bandwidth counters/charts remain available while its Livebox session is connected.

## Devices and diagnostics

Device lists preserve their router source. A device seen by both routers can appear twice; this is preferable to inventing ownership. Aliases, favorites and categories are local annotations, not router renames. Manufacturer, last activity, per-device traffic, QoS, blocking, IP reservations and Wake-on-LAN are not inferred or claimed by the new device view.

Diagnostics run against one explicitly registered, authorized destination: four ICMP requests, DNS resolution through the backend, a TCP connection to the selected port, or a traceroute limited to eight hops. Output and execution time are bounded. Internet public reachability is not inferred from an internal TCP success. CLI tools/privileges may be absent on a native Windows/Linux host; the error is displayed as unavailable. Docker installs ping, traceroute and OpenSSH.

## Guide rapide en français

Cette branche prépare la V4 et conserve la base 3.0. Le bureau classique reste disponible. Les identifiants sont saisis dans l’application authentifiée et ne sont pas publiés. Pour les fonctions Wi-Fi et NAT existantes, connectez aussi la Livebox et le TP-Link dans leurs outils V3. Les nouvelles sessions du registre servent à leurs propres lectures et actions confirmées.

Les rubriques affichent leurs limites : une API étudiée ne vaut pas validation sur tous les modèles. OpenWrt et SSH nécessitent une configuration volontaire ; les autres marques sans connecteur sont indisponibles. Les profils, observations et notifications sont stockés uniquement sur votre backend. Aucun accès au serveur du propriétaire du projet n’est nécessaire.

L’évaluation doit utiliser une installation séparée. Le développement de cette branche n’a ni redéployé le serveur Debian existant ni appliqué de changement à des équipements réels.
